CHAPTER 2

Storage Engine COMPLETE

A durable, crash-recoverable key-value engine — built correct in memory first, behind an interface, then made persistent with a write-ahead log.

Approach

The guiding principle: get the semantics right in memory behind a clean interface, then add durability underneath without changing callers. That interface is what later lets Raft depend on "a store" while staying ignorant of how bytes reach disk.

Store Interface

Every implementation satisfies one contract. Get reports a missing key with the sentinel ErrNotFound; the error return leaves room for disk-backed engines to surface I/O failures through the same signature. 

type Store interface {
    Get(key keva.Key) (keva.Value, error)
    Put(key keva.Key, value keva.Value) error
    Delete(key keva.Key) error
}

var ErrNotFound = errors.New("store: key not found")

In-Memory Store

A map guarded by a sync.RWMutex — many concurrent readers or one writer. Two correctness details matter:

  • Defensive copies. Because Value is []byte, the store copies on Put and Get so callers cannot mutate stored data through a slice they still hold.
  • Compile-time interface check. var _ Store = (*Memory)(nil) fails the build the instant Memory stops satisfying Store.
type Memory struct {
    mu   sync.RWMutex
    data map[keva.Key]keva.Value
}

var _ Store = (*Memory)(nil)

Write-Ahead Log

The write-ahead log is what makes the store durable, and it is worth understanding in depth — the same idea returns one level up as the Raft log.

The problem: crashes happen mid-write

A store that lived only in memory and periodically dumped itself to a data file has two failure modes on a crash. First, every write since the last dump is lost. Second, and worse: if the crash lands during a dump, the data file is now half-old and half-new, possibly unreadable — not just recent data lost, but all of it. The root cause is that updating data in place is not atomic: a single write may touch several bytes or pages, and a crash can leave it half applied.

The idea: log the intent before doing the deed

The write-ahead principle inverts the problem: before modifying state, first append a durable record of what is about to happen; only then apply it to memory. Every mutation follows the same four steps. 

1. encode the command       (Put k=v)
2. append it to the WAL
3. fsync                    ← now on disk, survives a crash
4. apply to the in-memory map

Why append-only changes everything

The log is append-only: existing bytes are never modified, only added to the end. Appending is the one file operation that is easy to make crash-safe, because a crash can damage only the tail — the record being written — never the records already durable before it.

In-place updateAppend-only log
A crash can corrupt…anywhere in the fileonly the last record
Old data at risk?yesno — untouched
Recoveryambiguous, often impossiblereplay from the start

The recovery contract

Invariant. State at any moment equals the result of applying, in order, every command in the log. The in-memory map is only a fast cache; the log is the source of truth.

Recovery is therefore a single loop, run on startup:

memory := empty
for cmd in ReadAll(wal):
    apply(cmd)   // Put → set, Delete → remove

Two properties make this safe:

  • Ordering — append order is apply order, so Put k=1 then Put k=2 always replays to 2.
  • Idempotency — replaying the same log twice yields the same state, so a crash during recovery is harmless: just replay again.

Durability layers: flush vs fsync

Written bytes do not reach the disk platter directly. They pass through layers, each of which can lose data on a crash. 

your []byte
   │  bufio.Writer.Flush()    hands bytes to the OS
   ▼
OS page cache                 in RAM — lost on power failure
   │  File.Sync()  ==  fsync   forces persistence to the device
   ▼
physical disk                 survives power loss ✓

Flush() only moves data from the process into the OS — enough if the process dies but the machine lives. fsync is the only call that guarantees bytes are on the physical device. Append does both, so a returned Append means truly durable, even across a power cut.

Durability vs throughput. An fsync is a real device round-trip (often 1–10 ms), so one fsync per append caps throughput. The standard remedy — revisited in the performance phase — is group commit: batch many appends behind a single fsync, amortizing the cost.

Record Format

An append-only file is just a byte stream. On replay we must know where each record starts and ends, and whether it is intact. The header answers both: each record is framed with a length and a CRC32 checksum. 

┌──────────┬──────────┬───────────────────────────────────────────┐
│ uint32   │ uint32   │ payload                                     │
│ length   │ crc32    │  op(1) · keyLen(4) · key · valLen(4) · val  │
└──────────┴──────────┴───────────────────────────────────────────┘
  └──────── 8-byte header ────────┘  read exactly one record at a time
length payload size crc32 integrity check op Put / Delete keyLen · key valLen · val
  • Length prefix makes records self-delimiting — no separators, so a value may contain any byte, including binary data.
  • Big-endian field encoding — stable across machines, ready for Raft to ship records between nodes.
  • CRC on replay catches silent bit-rot: a single flipped byte fails the checksum.

Failure Modes & Recovery

Replay distinguishes three situations, each mapping to a real event:

SituationMeaningResponse
Clean io.EOF at a boundarynormal end of logstop, return all records
io.ErrUnexpectedEOF (short read)crashed mid-append — torn tailstop cleanly, keep prior records
CRC mismatchcorruption in a complete recordreturn an error

The distinction between the last two is deliberate. A torn tail is expected — a crash during a write must not lose the writes before it — so it is tolerated. Corruption inside a complete record is not expected and signals real damage, so it is surfaced rather than silently skipped.

In the Wild & Growth

The write-ahead log is the backbone of durable systems:

  • PostgreSQL — the WAL is the crash-recovery and replication mechanism; data files are updated lazily from it.
  • LevelDB / RocksDB — every write hits the WAL before the in-memory memtable — exactly this log-plus-memory architecture.
  • Kafka — an append-only log of framed, checksummed records, exposed as a product.
  • etcd / Raft — the Raft log is a WAL: each entry is appended and fsync'd before it is acted on. Keva's Entry{Term, Index, Command} already has that shape.
The one weakness. An append-only log grows forever — a million Puts to one key leaves a million records. Compaction fixes this: periodically snapshot current state, then discard log records before the snapshot. Recovery loads the snapshot and replays only the tail. The same mechanism returns in Raft as log compaction / snapshotting.

Crash Recovery

The durable store composes the two proven pieces — the in-memory map and the write-ahead log — into one Store. It writes to the log before memory, and on open it rebuilds memory by replaying the log. 

type Durable struct {
    mem *Memory   // fast, queryable state
    wal *WAL      // durable, ordered history
}

Write path: log before memory

Every mutation is appended (and fsync'd) to the log first, and only then applied to memory. The ordering is the guarantee: a crash between the two is safe, because replay re-applies the committed command. The reverse order could leave memory ahead of the log and silently lose the write. 

func (d *Durable) Put(key, value) error {
    cmd := Command{Op: OpPut, Key: key, Value: value}
    if err := d.wal.Append(cmd); err != nil {   // 1. durable first
        return err
    }
    applyCommand(d.mem, cmd)                      // 2. then visible
    return nil
}

One apply path for writes and replay

A single function maps a Command onto state, used by both live writes and replay on open. Because recovery runs the exact same code as the original write, replayed state is identical to the state that was lost — not merely similar. 

// on open
for cmd := range ReadAll(path) { applyCommand(mem, cmd) }
// on write
applyCommand(d.mem, cmd)
The headline guarantee. Write with one instance, close, then open a fresh instance on the same file — the data is recovered. And because every append fsyncs, writes survive even a crash with no clean close: the log on disk is enough to rebuild state.

Compaction

The append-only log grows without bound — five hundred writes to one key leave five hundred records, and deleted keys keep their history. Compaction rewrites the log to the minimal set of writes that reproduce current state.

The insight: a snapshot of live state is a valid, minimal log. Capturing one Put per live key — no overwrites, no deletes — produces a log that replays to identical state at a fraction of the size.

The atomic swap

The live log cannot simply be truncated and rewritten in place — a crash mid-rewrite would destroy everything. Instead the compacted log is written to a temporary file and swapped in atomically. 

1. write records to a temp file      state.wal.compact
2. fsync the temp file               its contents are durable
3. rename temp → live path           atomic: a single step
4. fsync the directory               the rename itself is durable

rename is atomic on a POSIX filesystem: a crash leaves either the old complete log or the new one, never a partial mix. The directory fsync is the detail that is easy to miss — a rename updates a directory entry, and that update must be flushed for the swap to survive power loss.

Same idea, one level up. This is the storage-engine cousin of Raft snapshotting: a lagging follower receives a compacted snapshot instead of the entire log, and that snapshot is persisted with the same temp-write-then-rename technique.

An ordering invariant, and the limits of -race

Compaction and every write take a single lock, so that the order commands are appended to the log is exactly the order they are applied to memory. Without it, two concurrent writes to the same key could be logged in one order but applied in another — leaving live state and recovered state silently disagreeing.

Note. The race detector does not catch this: the map and the log are each mutex-guarded, so there is no data race — only a higher-level ordering invariant that must be reasoned about, not tooled away.

Property & Fuzz Testing

Hand-written tests cover the cases we thought of. Two randomized techniques cover the ones we did not.

Model-based property testing

Thousands of random Put / Delete / Compact / Restart operations run against both the store and a plain-map reference model; after every step the two must agree. A small key space forces frequent overwrites and deletes, and randomly interleaving compaction and reopen checks that durability and compaction hold under arbitrary sequences — not just tidy ones. Fixed seeds make any failure perfectly reproducible.

Fuzzing the decoder

Go's coverage-guided fuzzer feeds hundreds of thousands of arbitrary byte sequences to the replay decoder, asserting the one property a parser must guarantee: it never panics or hangs, always returning commands or an error. The decode loop is factored to read from an io.Reader so it can be fuzzed in memory, without touching disk.

A bug caught before it bit. The decoder read a 4-byte length prefix and then allocated a buffer of that size. A corrupt length — say 0xFFFFFFFF — would attempt a ~4 GiB allocation and crash the process: one bad byte in the log takes down the server on startup. The fix is a maxRecordSize cap checked before allocating. The rule is general: never trust a size field from untrusted bytes without bounding it.
Chapter complete. The storage engine is durable, crash-recoverable, self-compacting, and fuzz-hardened. Next comes the network layer, so the client can talk to the daemon over the wire.
