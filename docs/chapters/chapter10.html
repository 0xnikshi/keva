Nine chapters in, Keva is a complete distributed key-value store: correct, fault tolerant, operable, and fast. This last chapter steps back — what was built, how to run it, and how it is shown to be right.

Running it

Two binaries: kevad (the daemon) and keva (the client). Build them, start three nodes, and write to any one — a follower forwards to the leader, and every node reads back the same value. 

make build
./bin/kevad --id n1 --addr :7070 --peers n2=localhost:7071,n3=localhost:7072 --data ./data/n1
# ...n2 and n3 likewise...
./bin/keva --addr http://localhost:7070 put city pune
./bin/keva --addr http://localhost:7071 get city      # -> pune, from any node

The whole fault-tolerance story — cluster up, a write, a leader killed, a new leader elected, still serving — runs as one self-contained command: 

make demo

How it is shown to be right

Keva is not just asserted to be correct; it is checked as an adversary would attack it, all under the race detector. A linearizability checker verifies that concurrent client histories could have come from a single consistent register. A safety-invariant checker confirms, after every step, that no two leaders share a term, that logs match, and that committed entries never diverge. A randomized chaos suite throws partitions, elections, crashes, and snapshots at the cluster and asserts nothing committed is ever lost. Each checker is itself fed a hand-built violation, so a silent pass means something.

And it is fast where it counts: the two costly steps of consensus — the majority round trip and the fsync — are amortized across concurrent operations, with benchmarks to show it. The full feature list, quickstart, and numbers live in the project README.

What it is. A fault-tolerant, strongly consistent, Raft-backed key-value store — writes replicate through consensus, reads are linearizable, clients talk to any node, the cluster reshapes its own membership and survives failures, and all of it is proven under chaos and tuned for throughput.
Where it could go next. An append-only persistence log instead of rewriting state each flush; follower reads for workloads that tolerate bounded staleness; multi-key transactions; and a deterministic network simulator to fold the linearizability and invariant checkers into one harness. The core is done — these are the next climbs.
