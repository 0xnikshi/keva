CHAPTER 9

Performance COMPLETE

Correct and hardened, Keva is now made fast. The theme is amortization: the costly steps of consensus — a round trip to a majority, an fsync — should be paid once for many operations, not once per operation.

Batched Reads

A linearizable read is not free: before the leader may answer, it must confirm it is still the leader by hearing back from a majority (the ReadIndex round from Chapter 5). Done naively, every read pays its own round trip, so read throughput is capped at one majority confirmation per read — wasteful when many reads arrive at once, since a single confirmation would have vouched for all of them.

Coalescing the confirmation

Reads now queue and share rounds. Each request registers itself and the first one starts a processor; the processor takes everything waiting, performs one confirmation round, and hands that result to the whole batch. Requests that arrive while a round is in flight form the next batch — so a read is always served by a round that began at or after its own arrival, which keeps it linearizable. 

func (r *Raft) processReads() {
    for {
        batch := r.takeQueuedReads()   // everything waiting right now
        if len(batch) == 0 { return }
        idx, err := r.confirmReadIndex(ctx)  // ONE majority round
        for _, res := range batch {
            res <- readResult{idx, err}      // serve them all
        }
    }
}
Why it stays linearizable. The read index for a batch is captured after the batch is closed, so it is at least as recent as every request in it — each read still reflects everything committed before it began. A request that shows up mid-round is deferred to the next batch rather than served by a stale one.
Proven. With a brief delay holding each round open, twenty concurrent reads complete using just two confirmation rounds instead of twenty — the cost of confirmation is now shared across the batch, not paid per read.

Group Commit

Writes have their own per-operation tax. Each proposal was appended, persisted with its own fsync, and sent in its own replication round. fsync is the slow one — tens to hundreds of microseconds of real disk work — so paying it once per write throttles the whole write path. The fix is the same shape as batched reads, applied to the costly steps: coalesce concurrent proposals into one persist and one round.

Append, then flush together

A proposal appends its entry under the lock and then joins a flush. The first proposal in flight starts a processor; others queue behind it. The processor persists once — a single fsync covering every entry the batch appended — and runs one replication round that carries them all. A proposal that arrives mid-flush joins the next batch, so its entry is always covered by a round that began after its append. 

func (r *Raft) flushLoop() {
    for {
        batch := r.takeFlushWaiters()        // everyone waiting now
        if len(batch) == 0 { return }
        r.persist()                          // ONE fsync for the batch
        r.replicate()                        // ONE round carrying them all
        for _, done := range batch { close(done) }
    }
}
Commit never outruns the fsync. Group commit introduces a hazard: a second proposal can append while a batch is mid-flight, so the log can hold entries that are not yet persisted. The commit index is therefore capped at a persistedIndex that only advances inside persist — an entry can be committed, and so acknowledged, only once the fsync that covers it has run. Durability is never traded for throughput.
Proven. With a round held briefly open, twenty concurrent writes complete using two persists instead of twenty — the fsync cost is amortized across the batch — while every existing correctness test, including the chaos and linearizability suites, still passes.

Benchmarks

Optimizations are worth only what they measure, so the gains are pinned down with Go benchmarks: the raw store as a ceiling, and the replicated read and write paths both serially and under concurrency. The consensus numbers use the in-memory transport, so they isolate protocol overhead from disk and network.

Benchmarkns/opWhat it shows
Memory Put / Get~80the bare store — the ceiling consensus works below
Submit, serial~21,000one proposal's own round, nothing to batch

ReadIndex, parallel~420batched confirmation makes reads cheap

The headline is the serial-versus-parallel write gap: the same operation costs about half as much per write once there is concurrency to coalesce, which is group commit earning its place. Reads under concurrency are an order of magnitude cheaper still, since a batch of them resolves against one confirmation round.

Honest framing. These measure protocol overhead, not a production deployment: the transport is in-memory and the store fits in RAM. Real fsync and network latency dominate on real hardware — which is exactly why batching them matters, and why the numbers that improve here are the ones that would hurt most there. Making persistence itself cheaper (an append-only log instead of rewriting the whole state each flush) is the natural next optimization.
