CHAPTER 9

Performance IN PROGRESS

Correct and hardened, Keva is now made fast. The theme is amortization: the costly steps of consensus — a round trip to a majority, an fsync — should be paid once for many operations, not once per operation.

Batched Reads

A linearizable read is not free: before the leader may answer, it must confirm it is still the leader by hearing back from a majority (the ReadIndex round from Chapter 5). Done naively, every read pays its own round trip, so read throughput is capped at one majority confirmation per read — wasteful when many reads arrive at once, since a single confirmation would have vouched for all of them.

Coalescing the confirmation

Reads now queue and share rounds. Each request registers itself and the first one starts a processor; the processor takes everything waiting, performs one confirmation round, and hands that result to the whole batch. Requests that arrive while a round is in flight form the next batch — so a read is always served by a round that began at or after its own arrival, which keeps it linearizable. 

func (r *Raft) processReads() {
    for {
        batch := r.takeQueuedReads()   // everything waiting right now
        if len(batch) == 0 { return }
        idx, err := r.confirmReadIndex(ctx)  // ONE majority round
        for _, res := range batch {
            res <- readResult{idx, err}      // serve them all
        }
    }
}
Why it stays linearizable. The read index for a batch is captured after the batch is closed, so it is at least as recent as every request in it — each read still reflects everything committed before it began. A request that shows up mid-round is deferred to the next batch rather than served by a stale one.
Proven. With a brief delay holding each round open, twenty concurrent reads complete using just two confirmation rounds instead of twenty — the cost of confirmation is now shared across the batch, not paid per read.
