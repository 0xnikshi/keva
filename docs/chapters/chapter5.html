CHAPTER 5

Replicated KV IN PROGRESS

Wire the Raft core to the storage engine so the cluster serves consistent reads and writes: every write travels through consensus before it becomes visible.

Approach

Writes and reads take different paths. A write is proposed to Raft, replicated to a majority, committed, and only then applied to the store — so every node applies the same writes in the same order. A read is served from the local store, the materialized result of that replicated log. 

write:  client → server → raft.Submit → commit → Apply → store
read:   client → server → store.Get

The Store as State Machine

Raft applies committed commands to whatever satisfies its one-method StateMachine interface. A small adapter bridges the store to it, keeping Raft ignorant of storage and the store ignorant of consensus — the wiring lives in one place. 

func (f *Store) Apply(cmd keva.Command) {
    switch cmd.Op {
    case keva.OpPut:    f.store.Put(cmd.Key, cmd.Value)
    case keva.OpDelete: f.store.Delete(cmd.Key)
    }
}
Design decision: the Raft log is the source of truth. Once writes flow through Raft, the Raft log already provides durability and ordering, so the state machine is the simpler in-memory store, rebuilt by replaying the log. Keeping the storage engine's own write-ahead log on top would mean logging everything twice. This mirrors how etcd layers its key-value state on the Raft log.

The Write Path

The server no longer writes to the store directly. It proposes the command through a Proposer interface (satisfied by a Raft node) and lets consensus carry it to the store. Reads still come straight from the store. 

func (s *Server) handlePut(w, r) {
    // ...decode body...
    if _, err := s.raft.Submit(keva.Command{Op: OpPut, Key: key, Value: req.Value}); err != nil {
        s.writeSubmitError(w, err)   // 503 if not the leader
        return
    }
    w.WriteHeader(204)
}

A write that reaches a non-leader fails with 503 Service Unavailable — a retryable signal. Routing the client to the actual leader comes in a later step; for now the single-node daemon is always its own leader.

Proven. A write proposed through a real Raft node is replicated, committed, applied to the state machine, and then read back — the full consensus-to-storage path, exercised end to end. The kevad daemon now runs a Raft node backing the store.

Node-to-Node Transport

The Raft core reaches peers through a Transport interface. The HTTP implementation sends each RPC as a JSON POST to the peer's /raft/* endpoint, addressing peers by ID through an id → URL map. 

func (t *Transport) RequestVote(peer string, args raft.RequestVoteArgs) (raft.RequestVoteReply, error) {
    var reply raft.RequestVoteReply
    err := t.post(peer, "/raft/vote", args, &reply)
    return reply, err
}

Each daemon serves two route trees on one port: /v1/* for clients and /raft/* for peers. An incoming RPC is decoded and handed straight to the local node's RequestVote / AppendEntries. 

mux.Handle("/v1/",   server.New(node, store).Handler())  // clients
mux.Handle("/raft/", rafthttp.Handler(node))             // peers

Nodes are configured with --id, --addr, and --peers id=addr,…. With no peers a node is a single-node cluster; with peers it elects a leader and replicates over the network.

Proven as a cluster. Three nodes start, elect a single leader, and a value written to the leader is read back identically from all three — replication over real HTTP.

Leader Forwarding

Only the leader may accept writes, but a client should be able to talk to any node. A follower that receives a write forwards it to the current leader and relays the response, so the client never has to find the leader itself. 

func (s *Server) handlePut(w, r) {
    if !s.raft.IsLeader() {
        s.forwardToLeader(w, r)   // proxy to the leader, relay its reply
        return
    }
    // ...leader: decode and Submit...
}

Each node knows the leader because a valid AppendEntries carries the leader's ID; the node records it and maps it to a URL through the same peer map the transport uses. When no leader is known yet, the write gets a retryable 503.

Proven. With three nodes running, a write sent to any node — leader or follower — is accepted, and every key reads back consistently from all nodes. Clients are freed from tracking leadership.

Linearizable Reads

Reading from any local store risks stale data: a follower may lag, or a deposed leader may not yet know it was replaced. A linearizable read must reflect the latest committed write, so reads are served by the leader using the ReadIndex protocol.

  1. Followers forward reads to the leader, as they do writes.
  2. The leader records its commit index, then heartbeats a majority to confirm it is still the leader — ruling out a newer leader that may have committed writes it has not seen.
  3. With leadership confirmed and the state machine applied up to that index, it reads its local store.
if _, err := s.raft.ReadIndex(); err != nil {   // confirm leadership
    s.writeSubmitError(w, err)
    return
}
val, err := s.store.Get(key)                     // now linearizable
Proven. A value written through the leader is read back immediately and identically from every node — no replication-lag window — because all reads resolve against the leader's confirmed, committed state.
Trade-off. Every read now costs a heartbeat round to confirm leadership, and all reads funnel through the leader. That is the price of linearizability; systems that tolerate slightly stale reads often add a faster "read from any follower" mode too.
