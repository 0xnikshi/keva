CHAPTER 6

Cluster Operations COMPLETE

Make the cluster durable and elastic: recover state after a crash, compact the log so it does not grow forever, and change membership on a running cluster.

Persistence & Recovery

When Raft was first wired in, each node kept its log only in memory — a restart lost everything. Now the Raft state (term, vote, log) is persisted to disk with the same crash-safe recipe used throughout Keva: encode, write a temp file, fsync, rename, fsync the directory.

Rebuilding the store on restart

The state machine — the in-memory store — is not persisted. It is rebuilt on every restart by replaying the recovered log. Because applying a command is idempotent, replaying the whole committed log reconstructs exactly the state that was lost.

The recovery subtlety. On restart the log is reloaded, but the commit index is volatile and starts at zero. Raft's safety rule says a leader may only commit entries from its own term by counting replicas — so the reloaded, older-term entries would never re-commit, and never re-apply. The store would stay empty.

The no-op on election

The fix is a classic Raft technique: when a node becomes leader it appends a no-op entry in its current term. Committing that no-op advances the commit index past all the older entries, which then apply in order — rebuilding the store. No-op entries carry no command, so they are skipped when applying. 

func (r *Raft) becomeLeader() {
    r.state = Leader
    // A no-op in the current term; committing it re-commits (and re-applies)
    // everything before it — how a restarted cluster recovers its state.
    r.log = append(r.log, keva.Entry{Term: r.currentTerm, Index: r.lastLogIndex() + 1})
    r.persist()
    // ...initialize per-peer replication...
}

Wiring

A node is given a storage path (the daemon's --data directory, one file per node). With a path set, cluster.New loads any saved state before the node starts and saves on every state change; with no path it runs in memory.

Proven. A value written to a running daemon survives killing the process and restarting it on the same data directory — recovered by replaying the persisted Raft log.

Snapshotting

The log only ever grows. Every write appends an entry, and a key written a thousand times keeps all thousand records even though only the last one matters. Left alone, the log consumes unbounded disk and makes restart recovery — which replays it — ever slower. Snapshotting breaks the cycle: the state machine already holds the result of the log, so we save that image and discard the entries that produced it.

The index problem

Discarding the front of the log breaks the one assumption the rest of Raft was built on: that entry N sits at slice position N-1. Once a prefix is gone, that arithmetic is wrong everywhere it appears. The fix is a single offset, logBase — the index of the last entry folded into the snapshot. The slice now holds entries logBase+1 onward, and one helper resolves any index through it, so the handler, the replicator, and commit-advance never index the log raw. 

// termAt returns the term of the entry at a log index, accounting for the
// compacted prefix. index == logBase refers to the snapshot's last entry.
func (r *Raft) termAt(index uint64) uint64 {
    switch {
    case index == 0 || index < r.logBase: return 0
    case index == r.logBase:               return r.logBaseTerm
    default:                               return r.log[index-r.logBase-1].Term
    }
}

Taking a snapshot

Compaction captures the state machine as of lastApplied, then drops every log entry up to that index. It holds the apply lock for the whole operation so no entry is applied between reading the index and capturing the image — the image and the boundary it claims to cover must agree. 

func (r *Raft) Snapshot(threshold int) (bool, error) {
    r.applyMu.Lock(); defer r.applyMu.Unlock()
    // ...skip if the log is short or nothing new is applied...
    data, _ := r.sm.Snapshot()           // state-machine image at lastApplied
    r.log = r.log[snapIndex-r.logBase:]   // discard the compacted prefix
    r.logBase, r.logBaseTerm = snapIndex, snapTerm
    r.snapshot = &Snapshot{LastIncludedIndex: snapIndex, LastIncludedTerm: snapTerm, Data: data}
    r.persist()
    return true, nil
}

Recovery from a snapshot

The snapshot is persisted alongside the log in the same crash-safe file. On restart, the state machine is rebuilt from the image in one step — Restore(data), no replay — and the log resumes past the boundary. The few entries committed after the last snapshot replay normally once a leader re-confirms them. 

if ps.Snapshot != nil {
    r.sm.Restore(ps.Snapshot.Data)             // rebuild state instantly
    r.logBase = ps.Snapshot.LastIncludedIndex  // log resumes after the boundary
    r.commitIndex, r.lastApplied = r.logBase, r.logBase
}
Proven. A node commits a run of writes, snapshots, and its log shrinks while lastLogIndex is unchanged and the next write still lands at the correct index. A fresh node rebuilt from the same file recovers its full state from the snapshot image alone, with no log to replay.

Catching Up a Follower

Compaction creates a gap. Ordinary replication works by sending a follower the entries after the last one it holds — but once the leader has compacted past that point, those entries no longer exist as log entries. A follower that was partitioned or crashed through a snapshot can never be caught up entry by entry: the history it needs is gone.

The answer is to send the result instead of the steps. When a follower trails the leader's snapshot boundary, the leader ships it the whole state-machine image in one InstallSnapshot RPC. The follower adopts it — restoring its state machine and resuming its log from the boundary — and the next round resumes ordinary replication for anything newer. The snapshot is a one-time jump to catch up, not the steady-state path. 

// In replicateTo: the peer's next entry is already compacted away.
if prevIndex < r.logBase {
    snap := r.snapshot
    r.mu.Unlock()
    r.sendSnapshot(peer, term, snap)  // ship the image, then resume normally
    return
}

Installing it

The receiver does the same term check as every RPC, then adopts the image: restore the state machine, move the log boundary, and advance its commit and applied indices to it. If it still holds the boundary entry and it matches, the tail past it is kept rather than discarded — a follower only slightly behind loses nothing it already had. 

r.sm.Restore(args.Data)                       // rebuild state from the image
r.logBase, r.logBaseTerm = args.LastIncludedIndex, args.LastIncludedTerm
r.commitIndex, r.lastApplied = max them to the boundary
Serialized with apply. Installing a snapshot restores the store, and applying committed entries writes to that same store. Both take the apply lock in the one order used throughout — apply lock before the state lock — so they never touch the store at once, and the race detector stays clean.
Proven. A follower kept offline while the leader commits writes and then compacts them away rejoins with no log entries left to replay — yet recovers the full state through InstallSnapshot and adopts the leader's snapshot boundary. The RPC travels over a dedicated HTTP endpoint, so a real networked cluster catches up a lagging node the same way.

Dynamic Membership

A cluster's node set is not fixed: machines are replaced, capacity is added, a dead node is swapped out. Changing membership on a running cluster is delicate — if the old and new node sets could each form a majority on their own, two leaders could be elected at once. Keva avoids that by changing membership one node at a time.

Why one at a time is safe. Add or remove a single node and any majority of the old configuration and any majority of the new one must overlap in at least one node — and that shared node won't vote for two leaders in the same term. Single steps make the change safe without the heavier machinery of joint consensus. Only one change is allowed in flight at a time, so the configurations never jump by more than one.

Configuration is part of the log

The membership isn't stored off to the side — it travels through the same log as the data. A change is a special entry carrying the new member set, and a node adopts a configuration the moment the entry enters its log, before it commits. That early adoption is a deliberate Raft rule: the nodes deciding whether the change commits must already be operating under the configuration being decided. 

// A config change is an ordinary log entry with a member set instead of a command.
r.log = append(r.log, keva.Entry{Term: r.currentTerm, Index: index, Config: members})
r.applyConfig(members)  // take effect now, on append — not on commit

Because the configuration rides in the log, every mechanism built earlier carries it for free: a follower learns a new member — and its address — from ordinary replication, a catching-up node gets the configuration in its snapshot, and a restarted node rebuilds the current membership by replaying its log.

Joining and catching up

Adding a node is proposing the change on the leader; the newcomer starts with an empty log and is brought current by the same replication and snapshot machinery as any lagging follower. The member entry carries the node's address, so every existing node learns how to reach it as the entry replicates. 

leader.AddNode(keva.Member{ID: "n4", Addr: "http://n4:8080"})
// → config entry replicates → n4 catches up via AppendEntries (or a snapshot)
Proven. A node added to a running two-node cluster joins, adopts the configuration, and catches up the committed data from an empty log; a removed node leaves the membership; and a second change is refused while the first is still uncommitted.
Known edges. Two refinements a production system adds: a removed node can time out and call disruptive elections (addressed with a pre-vote phase), and routing client requests to a brand-new node that becomes leader needs its address in the request-forwarding path too. The consensus-level change — safe, replicated, recoverable — is complete.
Chapter complete. Keva now survives restarts, bounds its log with snapshots, catches up far-behind nodes, and reshapes its own membership while running — the operational core of a real distributed store.
