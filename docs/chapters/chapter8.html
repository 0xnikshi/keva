CHAPTER 8

Hardening COMPLETE

Keva is correct; this chapter makes it robust — turning a system that works into one that behaves well when clients misbehave, the cluster stalls, or an operator needs to see what it is doing.

Durable Acknowledgment

A write handler used to return 204 No Content as soon as the command was proposed to Raft — appended to the leader's log and sent to peers — not once it had committed. That is a subtle but real lie: a proposed entry can still be lost if the leader is deposed before a majority stores it. A client that got a success could later find its write gone.

Why it slipped through. On a healthy, in-process cluster a single replication round almost always commits before the call returns, so the gap was invisible — until concurrency on CI produced a history the linearizability checker rejected. The fix is to make the acknowledgment mean what clients assume it means.

Waiting for commit, without polling

Submitting stays non-blocking at the Raft layer — it proposes and returns the entry's index. The new piece is AwaitCommit, which blocks until that index commits, leadership is lost, or the caller's context is done. It waits on a channel that is closed whenever the commit index advances or the node steps down, so there is no polling. 

func (r *Raft) AwaitCommit(ctx context.Context, index uint64) error {
    for {
        r.mu.Lock()
        switch {
        case r.state != Leader:        r.mu.Unlock(); return ErrNotLeader
        case r.commitIndex >= index:   r.mu.Unlock(); return nil
        }
        wait := r.commitWait
        r.mu.Unlock()

        select {
        case <-ctx.Done(): return ctx.Err()
        case <-wait:        // commit advanced or leadership changed; re-check
        }
    }
}

A deadline on every write

The server proposes, then awaits commit under a context bounded by both the client's request lifetime and a server timeout. The outcome maps to a precise status: committed is 204; a lost leadership or canceled request is a retryable 503; a commit that did not land in time is 504 Gateway Timeout. A stalled cluster can no longer hang a connection indefinitely. 

index, err := s.raft.Submit(cmd)      // propose
// ...
ctx, cancel := context.WithTimeout(r.Context(), commitTimeout)
defer cancel()
if err := s.raft.AwaitCommit(ctx, index); err != nil {
    s.writeSubmitError(w, err)        // 503 / 504
    return
}
w.WriteHeader(http.StatusNoContent)   // now the write is durable
Proven. Awaiting a committed entry returns at once; an isolated leader's write times out at its deadline rather than hanging; and a write in flight when the leader steps down fails with a clear, retryable error instead of a false success.

Request Limits & Backpressure

Every write now blocks until it commits, so a slow or stalled cluster leaves requests parked — each holding a goroutine, a connection, and memory. Without a limit, a burst of load or a wedged cluster piles work up without bound until the node falls over, taking even recoverable requests down with it. The defense is backpressure: cap the work in flight and shed the rest cleanly.

Shedding, not queuing

A counting semaphore — a buffered channel of fixed size — gates the client API. A request tries to claim a slot without waiting; if none is free, it gets 503 Service Unavailable with a Retry-After hint immediately, rather than joining an unbounded queue. Shedding keeps the node responsive and pushes the decision to retry back to the client, where it belongs. 

func (s *Server) limit(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        select {
        case s.sem <- struct{}{}:        // claimed a slot
            defer func() { <-s.sem }()
            next.ServeHTTP(w, r)
        default:                         // full: shed the load
            w.Header().Set("Retry-After", "1")
            writeError(w, http.StatusServiceUnavailable, "server overloaded")
        }
    })
}
Consensus is never starved. The limiter wraps only the client API (/v1). Raft's own peer RPCs (/raft) run on a separate handler and are never gated — so even while the node sheds client load, heartbeats, replication, and elections keep flowing, which is exactly what a stalled cluster needs to recover.
Proven. With the limit set to one, a request that parks in the commit wait holds the only slot; the next request is shed with 503 and a Retry-After header rather than blocking; and once the first completes, the slot frees and traffic flows again.

Observability

Until now the only window into a running node was its log lines. To operate a cluster you need to answer basic questions on demand: who is the leader, what term are we in, how far has the log committed and applied, and how much traffic is this node taking. A single GET /v1/status endpoint answers them, returning the node's Raft state alongside request counters as JSON. 

{
  "node": { "id": "n1", "role": "leader", "term": 7,
            "leader_id": "n1", "commit_index": 142, "last_applied": 142,
            "last_log_index": 142, "members": 3 },
  "requests": { "reads": 90, "writes": 50, "deletes": 2,
                "forwarded": 0, "overloaded": 3 },
  "inflight": 1
}

The Raft state comes from a single locked snapshot, so the numbers are mutually consistent. The counters are plain atomics bumped on each request path — reads, writes, deletes, writes forwarded to the leader, and requests shed by the limiter — giving a cheap picture of what the node is doing without a metrics dependency.

Observable under load. The status route is deliberately outside the in-flight limiter. A node is most interesting exactly when it is overloaded or wedged — so the endpoint that tells you so must keep answering even while every key-value request is being shed. commit_index versus last_applied, and a climbing overloaded count, are how an operator sees a stall as it happens.

Proven. After a mix of operations the endpoint reports the correct role and non-zero read/write/delete counts, and it still returns 200 while the key-value API is saturated and shedding load.

Read Safety After an Election

Chapter 7's linearizability checker kept failing intermittently, and it was right to: it had found a real stale read. A linearizable read is served at the leader's commit index — but a freshly elected leader's commit index can trail the true commit point. Until the new leader commits an entry from its own term, it cannot know how far the previous leader had actually committed, so a read taken in that window can miss an already-acknowledged write.

Why the window exists. Commit index is volatile — rebuilt after a restart or election, not carried over. A new leader only advances it by replicating a current-term entry to a majority. Between winning the election and that first commit, its commit index is whatever it happened to know as a follower, which may lag.

The read barrier

The fix is the rule from the Raft paper (§6.4): a leader must commit an entry from its current term before serving reads. Keva already appends a no-op on election — now that no-op doubles as a read barrier. ReadIndex waits for it to commit (reusing the same commit-wait channel as durable writes, so there is no polling) before confirming leadership and serving the read. The wait is bounded by the request's context, so a leader that cannot make progress returns a timeout rather than hanging. 

func (r *Raft) ReadIndex(ctx context.Context) (uint64, error) {
    if err := r.awaitReadBarrier(ctx); err != nil {  // §6.4: current-term commit first
        return 0, err
    }
    // ...confirm leadership by heartbeat, apply up to the read index, then serve...
}
Proven. A regression test elects a new leader whose no-op has not yet committed and shows a read correctly blocks (and times out) instead of returning a stale index — then succeeds once the no-op commits. Remove the barrier and the test fails, confirming it guards the real bug.

Graceful Lifecycle

Shutting a node down carelessly hurts the cluster in two ways: in-flight writes can be dropped, and if the node was the leader, the others sit idle until an election timeout elapses before electing a replacement — a serving gap on every restart. A graceful shutdown closes both: drain in-flight work while still leader, then hand leadership off deliberately.

Drain, then hand off

The daemon already stops accepting new connections and waits for active requests to finish (http.Server.Shutdown) — and it does this before giving up leadership, so in-flight writes commit normally rather than failing. Only then does it transfer leadership and stop the Raft loop. 

srv.Shutdown(ctx)              // stop new work, let in-flight writes commit
if node.IsLeader() {
    node.TransferLeadership(ctx)  // install a new leader before leaving
}
node.Stop()                    // halt the Raft loop

Leadership transfer

Rather than vanish and let the cluster discover the loss by timeout, the leader uses the Raft handoff (§3.10). It brings a follower fully up to date, stops its own heartbeats so it will not keep that follower's election timer alive, and sends a TimeoutNow RPC — telling the follower to start an election immediately. Because that follower's log is current, it wins at once, and the old leader steps down having confirmed a successor. 

// On the departing leader:
r.transferring = true                 // go silent so the target's timer fires
r.transport.TimeoutNow(target, ...)   // "start your election now"
// On the target follower:
func (r *Raft) TimeoutNow(args) { r.electionTimeout = 0 }  // elect on next tick

The handoff only targets a follower that is fully caught up, so the new leader never lacks a committed entry. If none qualifies, the node falls back to a plain stop and the survivors elect the normal way — correct, just not seamless.

Proven. A follower told to time out now wins on its next tick without waiting its full timeout, and a stale-term TimeoutNow is ignored. End to end, a leader transfers leadership and a different node is serving promptly, with the data intact.
Chapter complete. Keva is now hardened for real operation: writes are acknowledged only once durable, overload is shed instead of absorbed, the node is observable even under stress, reads stay linearizable across elections, and shutdown hands off cleanly. Next chapter: performance.
