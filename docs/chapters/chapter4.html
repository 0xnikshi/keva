CHAPTER 4

Raft Consensus IN PROGRESS

Turn single-node Keva into a fault-tolerant cluster that agrees on one ordered log, using the Raft consensus algorithm.

The Problem

Raft keeps a cluster of servers in sync despite crashes and network splits, using a replicated state machine: if every server applies the same commands in the same order, they all reach the same state. The problem therefore reduces to agreeing on one ordered log of commands — which is consensus.

Keva already applies an ordered log to reach state — the storage engine replaying its write-ahead log. Raft is the part that decides what that log contains across the whole cluster.

One Leader Owns the Log

Rather than have all servers negotiate as equals, Raft elects a single leader as the source of truth. Clients send commands to the leader; it appends to its log and replicates to followers; once a majority store an entry it is committed and applied on every node. Everything in the algorithm is either electing a leader or replicating the log.

The Three Roles

Every node is always in exactly one of three states.

RoleBehaviour
FollowerPassive; responds to the leader and to candidates. The default.
CandidateA follower that timed out waiting for a leader and is campaigning for votes.
LeaderWon an election; handles clients, sends heartbeats, replicates the log.

The flow is Follower → (timeout) → Candidate → (wins majority) → Leader. A leader that sees a newer term steps back down to follower.

Terms

Time is divided into numbered terms, each beginning with an election, with at most one leader per term. Any node that sees a term higher than its own adopts it and becomes a follower; a message from an older term is rejected as stale. Terms are a logical clock that replaces wall-clock time, which cannot be trusted across machines.

The Two RPCs

The entire protocol is two remote calls.

RequestVote candidates gather votes AppendEntries leader replicates entries; empty = heartbeat

Elections use the first; log replication uses the second.

Why Majority Works

Commit requires a majority, and the reason is elegant: any two majorities overlap in at least one node. A committed entry lives on a majority; any future election winner also needs a majority; so the winner is guaranteed to have seen the committed entry. Committed data can never be lost across a leader change. A cluster of N nodes tolerates ⌊(N−1)/2⌋ failures — 1 of 3, 2 of 5.

Node Skeleton & State

The node data model follows the Raft paper's state layout, split into two categories. The split is safety-critical.

FieldCategoryWhy
currentTermpersistentthe latest term seen
votedForpersistentwho this node voted for this term
logpersistentthe replicated command entries
statevolatilethe current role, safe to rebuild on restart
Why persistence is safety-critical. Suppose a node votes for candidate A in term 5, then crashes. If it forgot the vote on restart, it could vote for candidate B in the same term 5 — two leaders in one term, which breaks everything. So currentTerm and votedFor must reach stable storage before the node acts on an RPC.

1-based log indices

Raft numbers entries from 1; index 0 means "empty, before the log". The slice holds entries 1..N, so the last index is simply the length, and an empty log reports index 0 / term 0. These two values drive the election safety check in the next step. 

func (r *Raft) lastLogIndex() uint64 { return uint64(len(r.log)) }

becomeFollower — the universal step-down

The most-called transition in Raft. Any time a node sees a higher term it adopts the term, drops to follower, and clears its vote — a new term means a fresh vote to give. Centralizing it means every RPC handler just calls it. 

func (r *Raft) becomeFollower(term uint64) {
    r.state = Follower
    r.currentTerm = term
    r.votedFor = ""   // fresh term → vote available again
}
Locking convention. Exported methods take the mutex; internal helpers assume the caller already holds it. RPC handlers lock once at the top and call helpers freely — never double-locking a non-reentrant mutex.
